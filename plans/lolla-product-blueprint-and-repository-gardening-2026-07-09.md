## Executive Conclusion

Lolla should be developed as one product with one primary promise:

> Take a serious human–LLM conversation, preserve it, identify how the reasoning may be structurally fragile, apply source-backed challenge pressure, ask the reasoning agent to reconsider, and leave a self-explaining record of what happened.

The product is promising because the first fresh run produced pressure that changed the actual decision path, not only the wording. It exposed prestige being used as evidence, an untested commitment signal, a capacity bottleneck, missing evidence gates, and success criteria defined after action. The revised answer introduced a private validation path, explicit gates, stop rules, and decision branches while preserving the user's legitimate fear of losing momentum.

That is meaningful value.

It is not yet proof that Lolla reliably understands conversations or that its graph adds unique value. Two immediate extractions of the same six-turn conversation disagreed about which constraint and dropped thread mattered. The deterministic graph is currently fed by fact-bearing probabilistic interpretations rather than a clean abstract reasoning-pattern packet. A strong direct critic might have produced some of the same improvement.

The correct strategic stance is therefore:

- continue building the core;
- stop adding peripheral surfaces until the core is validated;
- make interpretation stability and graph contribution falsifiable;
- treat the reasoning receipt as proof of observable process, not proof of quality;
- garden the repository before sharing it broadly;
- separate the shareable product from the historical laboratory and potentially proprietary substrate.

The semantic-validation cases, active/edge/weak/parked portfolio layers, and
Case 09 diagnostic now exist. The next action is not another extractor, new
semantic reader, graph expansion, or broad share-readiness program. It is one
correctly frozen paired downstream test on an untouched holdout, followed by
exact review of whether Lolla pressure was used, rejected, forced, or lost.
Repository gardening remains subordinate and must not interrupt this core
evidence loop.

## The Big Picture

Lolla has three connected product layers, but only one is the current critical path.

```text
1. CORE REASONING AUDIT — prove now

verbatim conversation
        ↓
source-grounded joint-process interpretation
        ↓
fact-free reasoning-pattern projection
        ↓
deterministic graph selection and source-backed pressure
        ↓
real context reattached for reconsideration
        ↓
revised answer with explicit changes, rejections, and unknowns

2. REASONING WORK RECEIPT — strengthen after the core works

source + interpretation + patterns + routes + pressure + revision lineage
        ↓
self-explaining one-run package for a human or future agent

3. MENTAL MODEL TEACHER — preserve but defer

selected models + source corpus + relations + case application
        ↓
learning experience and graph visualization
```

These are not three unrelated products.

- The audit decides what pressure matters.
- The receipt explains how the audit happened.
- The Teacher can later explain the models used by the audit.

They should not mature at the same time. If the audit is not useful, the receipt documents weak work and the Teacher explains models that did not improve the decision. The core audit therefore owns the roadmap.

## What We Have Figured Out

### 1. The audited object is the joint process

Lolla must not audit only the last assistant answer. It must understand the interaction between the user and assistant:

- what the user initially asked;
- what assumptions the assistant accepted;
- what the user corrected or challenged;
- what constraints appeared later;
- whether the assistant changed position or merely acknowledged the correction;
- which questions were answered, under-carried, or dropped;
- which options remained live, were rejected, or were never considered;
- where urgency, status, fear, or framing influenced both participants;
- what the audit pressure later changed.

The system currently preserves the source conversation well but represents this temporal process only partially.

### 2. Facts must be preserved but should not drive model selection directly

The intended boundary is controlled decontextualization:

1. Preserve the full factual conversation as the source of truth.
2. Interpret source-linked reasoning events and patterns.
3. Project only abstract reasoning mechanisms into graph routing.
4. Reattach facts after pressure is selected so the challenge can be applied responsibly.

Examples of allowed abstract selection signals:

- authority signal treated as evidence;
- missing denominator;
- bottleneck acknowledged but not gated;
- success criteria defined after commitment;
- one-sided downside treatment;
- no reversal condition;
- user correction acknowledged but not integrated;
- initial frame persists after the operative question changes.

Names, company details, exact amounts, dates, raw quotes, and desired outcomes should stay outside graph selection.

The current runtime does not enforce this boundary.

### 3. The old live path and newer Decision Work path serve different jobs

The old live path is compact and automatic. It feeds the pressure lanes.

The newer Decision Work path is broad and retrospective. It can describe options, influence, changed direction, useful or noisy friction, lost value, overcorrection, evidence limits, and handoff status.

The correct plan is not to merge all fields immediately. Every field needs a demonstrated job:

- selection-critical;
- application-critical;
- accountability-critical;
- experimental or unnecessary.

A likely winning architecture is a narrow shared semantic kernel with two projections:

- a pre-audit operational projection;
- a richer post-audit accountability projection.

This remains an evaluation hypothesis, not an implementation decision.

### 4. A receipt proves observable work, not reasoning quality

The one-run package should prove:

- what source was captured;
- what process ran;
- what interpretations were generated;
- what patterns and models were selected;
- what pressure was presented;
- what the reviser used, rejected, or deferred;
- what changed in the answer;
- which artifacts exist and match their hashes;
- what remains unknown or unreviewed.

It cannot prove:

- the advice is correct;
- the reasoning is deep because it is long;
- the graph selected the best model;
- the human agrees;
- the action is safe;
- a clean run is a good run.

Therefore no aggregate grade, green badge, or “proof of quality” score should be added.

The July 10 reasoning-trust research intake reinforces this boundary but does
not change the implementation roadmap. It supports fluency risk, frame
inheritance, sycophancy, multi-turn drift, productive friction, and reasoning
custody as research hypotheses. Its technical proposals—typed lens graphs,
search, multi-agent critique, memory, optimization, and symbolic planners—are
context, not backlog. Exact empirical claims from that mixed primary,
preprint, and secondary-source bundle require source verification before use
in public product or marketing claims.

### 5. Cross-run memory and organizational knowledge are deferred

The vision of stacking run records into a project knowledge base remains plausible. It is not the current product problem.

Before building search, comparison, organizational memory, GraphRAG, or a second brain, one run must reliably:

- understand;
- abstract;
- pressure;
- revise;
- explain itself.

## How Useful Is The Current System?

### The most credible current value

Lolla is currently most useful as a **structured challenge generator with process custody**.

It can make a fluent answer less easy to trust by forcing concrete questions such as:

- What evidence is carrying this recommendation?
- Would the decision survive if the prestigious name or vivid example disappeared?
- Which constraint is actually binding?
- What would falsify the recommendation?
- What must be true before commitment?
- Which reversible path was omitted?
- What did the assistant acknowledge without integrating?
- What value would be lost by overcorrecting toward caution?

In Run 01, those questions produced a decision-useful delta. The public-launch recommendation became a private validation sequence with commitment, capacity, permission, learning, and stop gates.

### What the system tells us today

The current system can tell us, with different confidence levels:

| System output | What it can responsibly tell us now |
| --- | --- |
| Verbatim capture | What was preserved from the conversation and whether turns were omitted. |
| Quote validation | Whether selected assistant passages literally appear in the captured source. |
| Compact extraction | A plausible summary of decision, constraints, frame, position, and dropped threads that must be checked against the source. |
| Pressure lanes | Which structural weaknesses, model tensions, frame alternatives, and uncovered dimensions the configured prompts surfaced. |
| Deterministic trace | How supplied labels and candidates were routed, selected, capped, or suppressed under declared rules. |
| Revised answer | What the revising agent changed after considering the pressure. |
| Ledgers | What the reviser says it used, rejected, deferred, or kept private. |
| Receipt and hashes | Which artifacts exist, whether custody is mechanically coherent, and which claims remain unsupported. |

### What it does not tell us yet

It cannot yet reliably tell us:

- that the conversation interpretation is stable;
- that every important user correction or assistant stance was captured;
- that model selection is independent of topic and case facts;
- that the graph added more value than direct criticism;
- that selected pressure was the best pressure;
- that the revised advice is correct;
- that the user found the revision useful;
- that the result improved a real-world outcome.

### Current usefulness scorecard

This is a status map, not an aggregate score.

| Dimension | Current read | Why |
| --- | --- | --- |
| Source preservation | Strong | Full conversation and artifact custody work when capture is complete. |
| Challenge relevance | Promising | Run 01 surfaced several source-aligned mechanisms. Existing reviewed cases also show useful friction. |
| Action-level revision | Promising | Run 01 changed question, sequence, gates, and stop conditions. Earlier reviewed cases show similar candidates. |
| Preservation of user intent | Partial | Run 01 preserved urgency, but current extraction can lose user pressure and values. |

| Cold-reader handoff | Partial | Private Markdown is rich, but interpretation is thin and status language conflicts. |

### Where we stand in the roadmap

We are between **Phase 3 — graph contribution and pressure quality** and
**Phase 4 — gated runtime integration**.

- Phase 1 produced a retained offline semantic base and exposed material
  placement and temporal gaps. It is sufficient for continued experiments,
  not complete conversation understanding.
- Phase 2 produced reasoning-pattern and active/edge/weak/parked portfolio
  contracts in shadow. Its first frozen invariance experiment failed, although
  the deterministic fact-leak and custody layer worked.
- Phase 3 completed one directional paired case and one protected-edge case.
  Neither passed the full clean-accountability gate, so graph contribution is
  still unproven.
- Phase 4 is **not authorized**. The active next milestone is exact
  pressure-custody hardening plus a clarified joint-process abstraction,
  followed by one new paired holdout and new invariance fixtures.

### Safe product claim today

> Lolla preserves a strategic AI conversation, applies structured source-backed challenge pressure, can produce decision-relevant revisions, and leaves an inspectable record of the process.

### Claims we should not make yet

- Lolla reliably improves reasoning.
- Lolla proves reasoning quality or proof of work.
- The graph selects the right mental models.
- The system is deterministic end to end.
- Lolla removes LLM bias.
- The receipt certifies correctness or safety.
- Conversation Understanding is complete because an extraction exists.

## One Plan, Two Coordinated Tracks

The project should proceed through one program with two tracks.

### Track A — Core Product Evidence

Prove that the semantic and graph loop creates useful incremental pressure.

### Track B — Repository And Share Readiness

Make the project understandable, reproducible, legally reviewable, and safe to share.

Track B is deferred until the founder reactivates sharing. Only hygiene that is
directly exposed by core experiments—such as credentials, absolute paths in a
checked-in result, broken setup, or unclear canonical status—may interrupt
Track A. Deeper cleanup and archiving wait for the integration decision.

## Roadmap And Gates

### Phase 0 — Share-Safe Foundation Slice

Goal: remove the few blockers that would make the next core experiment hard to reproduce or a private repository share irresponsible.

Current status: deferred. This phase resumes when sharing becomes an active
goal; it is not a prerequisite for the current evidence batches.

This slice is capped at five outputs:

1. Freeze the current state and preserve Run 01 plus the recent evidence set.
2. Create the short canonical reader path: product, current state, live architecture, roadmap, and development setup.
3. Declare Python 3.12, dependencies, one setup command, one focused test command, and a minimal CI check.
4. Remove or parameterize personal absolute paths on live and share-facing surfaces; run secret and privacy scans.
5. Mark the current code/substrate distribution boundary and the unresolved rights question prominently.

Exit gate:

- a selected collaborator can clone, install, run the focused checks, understand the current claim and limitations, and locate Run 01 without reading historical PR files;
- no runtime behavior changes and no historical deletion;
- unresolved dataset rights are visible rather than silently covered by the root code license.

Stop rule:

- once these five outputs pass, begin Phase 1 even if deeper gardening remains;
- do not inventory all 4,687 files as a prerequisite;
- classify a file family only when it blocks sharing, is reached by the live runtime, or is a candidate for the next archive move.

### Phase 1 — Core Semantic Corpus And Two-Path Evaluation

Goal: determine what conversation meaning the live path truly needs.

Deliverables:

- a 12-case core corpus with exact source and artifact hashes;
- positive, negative, invariance, and adversarial cases;
- current extraction compared with default IR, three existing specialists, narrow missing specialists, and relevant Decision Work fields;
- stability checks over repeated identical extraction;
- one utility/timing/consumer decision for every retained field.

Exit gate:

- critical conversation fields are source-grounded and materially more stable than the current monolithic extraction;
- every live field has a demonstrated selection, application, or health consumer;
- post-audit fields remain outside live selection unless marginal value is shown.

Repository work during this phase is limited to items exposed by the experiment: dependencies, paths, fixtures, generated outputs, or dormant consumers that directly interfere with the live case.

### Phase 2 — Reasoning-Pattern Boundary

Goal: enforce controlled decontextualization.

Deliverables:

- minimal `reasoning_pattern_packet`;
- source semantic-item references;
- fact-leak linter;
- same-reasoning/different-facts pairs;
- same-facts/different-reasoning pairs;
- pattern-only shadow routing beside current routing.

Exit gate:

- graph input is invariant to irrelevant factual substitutions;
- graph input changes when the reasoning mechanism changes;
- names, entities, exact quantities, dates, and persuasive narrative do not leak into selection.

### Phase 3 — Graph Contribution And Pressure Quality

Goal: prove whether the curated graph creates incremental value.

Comparison arms:

1. direct critic over the transcript;
2. current Lolla route;
3. pattern-only route;
4. labels without graph relationships;
5. disabled or shuffled graph edges;
6. generic mental-model retrieval.

Review dimensions:

- pressure relevance;
- novelty;
- source fit;
- applicability;
- factual leakage;
- overlap/noise;
- changed action, threshold, sequence, evidence gate, or stop rule;
- lost value and overcorrection.

Exit gate:

- graph-backed pattern routing shows repeatable incremental value over simpler baselines;
- if it does not, simplify the graph role rather than adding graph sophistication.

### Phase 4 — Gated Runtime Integration

Goal: integrate only the smallest validated semantic and routing path.

Deliverables:

- shadow winner promoted behind a flag;
- rollback and old/new comparison artifacts;
- explicit semantic-health status;
- same-session reconsideration retained;
- reduced pressure saturation and candidate volume;
- cost and latency budget.

Exit gate:

- fresh runs reproduce offline results without unacceptable cost, latency, or regression;
- failures degrade honestly rather than producing plausible-looking clean output.

### Phase 5 — One-Run Receipt And Shareable Product

Goal: make the one-run package self-explaining without claiming quality.

Deliverables:

- full transcript;
- joint-process interpretation;
- fact-free pattern packet;
- graph trace and selected pressure;
- reviser dispositions;
- revised answer and memo;
- unresolved questions and missingness;
- separate statuses for source custody, interpretation, challenge execution, pressure accountability, revision lineage, and independent review.

Exit gate:

- a cold reader can explain what happened and what remains uncertain;
- no compact label is interpreted as correctness, certification, or action approval;
- `caller_action`, readiness, trace adequacy, and health language are coherent.

### Phase 6 — Deferred Product Expansion

Only after the previous gates:

- project knowledge base;
- cross-run comparison;
- organizational memory;
- Teacher learning experience;
- graph visualization;
- SDK/fresh-context reviser;
- agent continuation protocols;
- broader risk/control integrations.

## Recommended Repository Shape

### 1. Shareable product repository

Keep:

- `SKILL.md` and detailed step procedures;
- live engine modules reachable from production entrypoints;
- skill helpers and runtime CLIs;
- Observatory code needed by the active run;
- current graph and active compiled substrate;
- a small core evaluation corpus;
- focused core tests;
- canonical product, architecture, current-state, roadmap, development, and data-provenance docs;
- one short history pointer.

Target reader path:

1. `README.md` — what it is, current claim, quick start, honest status;
2. `docs/PRODUCT.md` — product thesis, users, current value, non-claims;
3. `docs/CURRENT_STATE.md` — built, partial, missing, evidence;
4. `docs/ARCHITECTURE.md` — live runtime and data boundaries;
5. `docs/ROADMAP.md` — the phases and gates in this blueprint;
6. `docs/DEVELOPMENT.md` — setup, tests, CI, release process;
7. `docs/DATA_PROVENANCE.md` — source, ownership, distribution, compiled-artifact policy.

The README should be approximately 200–300 lines, not 1,266. `PROGRESS.md` should not be a 4,276-line canonical status surface.

### 2. Historical research archive

Move out of the main product tree after hashing and tagging:

- historical `research/test-cases` and stability runs;
- pre-Step-6 experiment generations and replay outputs;
- old PR-numbered plans and handovers;
- most Codex-assisted reviews and generated report pairs;
- old compiled affordance snapshots and their quality reports;
- historical browser-review packets;
- superseded fixture packages whose only consumer is a historical artifact-lock test.

Recommended storage:

- an immutable `lolla-research-archive` repository or versioned release bundle;
- a manifest with source path, destination, hash, date, reason, and recovery command;
- a git tag on the product repository before removal.

Do not create a giant `archive/` directory inside the product repository. That preserves almost all clone, search, and comprehension cost.

### 3. Private substrate package

Treat the knowledge corpus separately from the MIT-licensed code.

Current concerns:

- 223 source briefing files are checked into `data/model_sources`;
- they include synthesized material, source quotes, claims, and book-derived content;
- the root MIT license does not explain whether it covers the dataset;
- manifests and compiled artifacts contain personal absolute source paths;
- the founder currently considers the corpus proprietary.

Recommended boundary:

- code license stated separately;
- dataset/substrate license stated separately;
- third-party notices and provenance review;
- private raw source briefs kept outside a public product repository unless distribution rights are confirmed;
- sanitized compiled runtime artifact distributed only under an explicit policy;
- source hashes and provenance preserved without personal machine paths.

This requires a rights/provenance review before public release. The plan does not make a legal conclusion about what may be distributed.

### 4. Dormant and experimental code quarantine

Do not delete dormant systems immediately.

Candidate families include:

- Decision Work / sidecar modules;
- Teacher modules;
- control-plane integration;
- dormant reasoning-substrate packet machinery using v4;
- Product Delta utilities;
- research-only V60 replay systems.

For each family, record:

- reachable from live runtime: yes/no;
- current owner and consumer;
- tests that protect it;
- data artifacts required;
- last evidence of product value;
- keep, extract, freeze, or retire decision.

Only then move it to a lab package or delete it from the shareable branch.

## The Immediate Development Sequence

Sharing work is deferred by founder choice. Development follows this order
without reopening product strategy after each small task.

### Batch 1 — close the downstream experiment contract

1. Select one untouched, lower-safety-risk holdout for a specific mechanism,
   not because its original answer is obviously poor.
2. Freeze and run Stage A once: source/capture, pipeline hashes, separate core
   and peripheral call ceilings, cost, novelty threshold, and stop rules.
3. If Stage A passes, review the source-traceable pressure packet and freeze
   Stage B **before either downstream call**: identical control/treatment
   model, prompt, cap, typed output, and exactly one call per arm.
4. Compare actual outputs for source fidelity, useful unique pressure,
   forcing, lost value, bloat, and disposition quality. Do not reward model
   names, candidate volume, or longer prose.

Exit gate: at least one trace-supported treatment delta is absent from the
strong control, changes a question, evidence gate, sequence, stop rule,
action, or important private guardrail, and does not lose more useful value
than the control. Clean equivalence is also a useful result and blocks
integration.

### Batch 2 — test the protected edge, not only the active shortlist

Use a false-stand-down or off-frame case to test whether the active/edge/weak/
parked portfolio gives a strange but plausible lens a serious hearing without
forcing it into public advice.

Exit gate: the candidate remains recoverable, receives a grounded use,
rejection, deferral, or private guardrail, and the receipt distinguishes
semantic rejection from technical non-consideration.

### Batch 3 — validate controlled decontextualization in shadow

Run provider-free and tightly bounded invariance pairs:

- same reasoning with changed names, industries, dates, and quantities should
  preserve graph pressure;
- similar facts with a changed reasoning mechanism should change graph
  pressure;
- the raw transcript remains available when pressure is re-applied.

Exit gate: irrelevant factual substitutions do not drive graph selection,
while real reasoning changes do. Failure leads to simplification or a better
probabilistic abstraction job, not deterministic keyword gates.

### Batch 4 — integration decision

Review the paired downstream case, protected-edge case, invariance results,
quiet-case evidence, costs, and failures together.

- If the evidence shows repeatable incremental consideration value, promote
  only the smallest portfolio/consumer path behind a flag with rollback.
- If strong controls repeatedly recover the same value, keep Lolla as an
  audit/receipt/navigation layer and simplify the graph's answer-generation
  role.
- If selected pressure forces or degrades answers, repair or reduce the
  consumer context before any integration.

No knowledge base, Teacher expansion, SDK productization, organizational
memory, broad repository cleanup, or marketing claim enters the critical path
before this decision.
